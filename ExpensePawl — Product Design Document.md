## 1. Overview

ExpensePal is a client-side single-page application for personal expense tracking. It runs entirely in the browser with no server infrastructure, no build pipeline, and no user authentication. All data is persisted in `localStorage`. The application includes a virtual pet subsystem rendered on HTML5 Canvas and a client-side PDF export capability.

This document describes the system architecture, data model, component interfaces, storage management strategy, and engineering trade-offs. It is intended for the implementing engineer.

---

## 2. Goals and Non-Goals

### 2.1 Goals

|ID|Goal|
|---|---|
|G-01|Functional expense CRUD with category management, search, and filtering.|
|G-02|Time-aggregated views: weekly, monthly, and yearly.|
|G-03|Multi-currency display formatting using the `Intl.NumberFormat` API.|
|G-04|Client-side PDF report generation via jsPDF (CDN).|
|G-05|Canvas-based virtual pet with autonomous animation, time-aware state, and user interaction.|
|G-06|Graceful `localStorage` capacity management with export-then-purge workflow.|
|G-07|Zero-dependency architecture excluding two CDN-loaded scripts (jsPDF, jsPDF-AutoTable).|

### 2.2 Non-Goals

- Server-side processing, authentication, or data synchronization.
- Data visualization (charts, graphs).
- Currency conversion or live exchange rates.
- Recurring expenses, budget thresholds, or alerts.
- PWA installation or service worker caching.
- Multi-language localization.

|---|---|---|

## 5. Component Design

### 5.1 ID Service

**Purpose:** Generate unique sequential identifiers for Expense and Category entities, following the auto-increment pattern used in relational databases.

**Strategy:** Monotonically incrementing integer counters, maintained independently per entity type. Each counter is persisted in `localStorage` and incremented atomically on every entity creation.

|Counter|Storage Key|Initial Value|Scope|
|---|---|---|---|
|Expense ID counter|`ep_counter_expense`|1|Expense entities|
|Category ID counter|`ep_counter_category`|1|Category entities|

**Allocation algorithm:**

1. On entity creation, the ID Service reads the current counter value from `localStorage`.
2. The value is assigned as the new entity's `id`.
3. The counter is incremented by 1 and written back to `localStorage` before the entity itself is persisted.
4. If the counter key does not exist (first-ever creation), it is initialized to 1.

**Format:** Positive integer (e.g., `1`, `2`, `3`, …).

**API surface:**

|Method|Description|
|---|---|
|`nextExpenseId()`|Returns the next available expense ID and increments the stored counter.|
|`nextCategoryId()`|Returns the next available category ID and increments the stored counter.|
|`peekExpenseId()`|Returns the next available expense ID without incrementing. Used for diagnostics only.|
|`peekCategoryId()`|Returns the next available category ID without incrementing. Used for diagnostics only.|

**Guarantees:**

- **Uniqueness:** Each ID is guaranteed unique within its entity type because the counter is strictly monotonic and never decremented or reset during normal operation.
- **Ordering:** IDs are strictly increasing, which implicitly reflects creation order and simplifies debugging.
- **Simplicity:** The scheme mirrors the familiar auto-increment primary key pattern in SQL databases (`AUTO_INCREMENT` in MySQL, `SERIAL` in PostgreSQL).

**Behavior during purge operations:**

The counter is **never reset** during the storage quota purge flow (Section 5.3). When expenses from a given month range are deleted, their IDs are retired permanently. New expenses continue to receive IDs from the current counter value. This prevents any possibility of ID reuse and preserves the integrity of any external references, such as those embedded in exported PDF reports.

**Behavior during data reset:**

When the user triggers a full data reset from the Settings panel (Section 5.7, ON-03), all `ep_*` keys including the counters are deleted. On the next entity creation, the counters reinitialize to 1.

**Trade-offs considered:**

|Alternative|Reason Not Chosen|
|---|---|
|`crypto.randomUUID()`|Unavailable in non-secure contexts (HTTP without localhost). Produces long opaque strings that complicate debugging.|
|Composite timestamp + random IDs|Unnecessarily complex for a single-user, single-device application with no distributed write concerns.|
|Hash-based IDs|Adds computation cost with no benefit for this use case.|

Sequential integer IDs are the appropriate choice because the application has a single writer (one browser tab for one user), no synchronization requirements, and no risk of concurrent ID allocation.

### 5.2 Time Service

**Purpose:** Provide consistent, timezone-aware date and time operations to all consuming modules.

**API surface:**

|Method|Returns|Description|
|---|---|---|
|`now()`|Number|Current Unix timestamp in milliseconds via `Date.now()`.|
|`todayISO()`|String|Current date in `YYYY-MM-DD` format, respecting the user's local timezone.|
|`formatCurrency(amount, currencyCode)`|String|Formatted monetary string using `Intl.NumberFormat` with the specified ISO 4217 currency code and the user's resolved locale.|
|`getWeekRange(date)`|Object `{start, end}`|ISO date strings for the Monday and Sunday of the week containing the given date.|
|`getMonthRange(date)`|Object `{start, end}`|ISO date strings for the first and last day of the month containing the given date.|
|`getYearRange(date)`|Object `{start, end}`|ISO date strings for January 1 and December 31 of the year containing the given date.|
|`getGreetingPeriod()`|Enum|Returns `MORNING`, `AFTERNOON`, `EVENING`, or `NIGHT` based on the current local hour.|
|`elapsedHoursSince(timestamp)`|Number|Hours elapsed between the given timestamp and `now()`.|
|`getUserTimezone()`|String|IANA timezone identifier via `Intl.DateTimeFormat().resolvedOptions().timeZone`.|

**Design note on time source:** JavaScript provides no built-in mechanism to synchronize with an authoritative time server (NTP). `Date.now()` reflects the device's system clock. The `Intl` API provides correct timezone-aware _formatting_ but does not correct an inaccurate device clock. This is an accepted limitation of a fully offline, client-only architecture. The edge case of an incorrect device clock is documented in Section 8.

### 5.3 Storage Service

**Purpose:** Centralize all `localStorage` interactions. Provide quota error handling and the export-then-purge workflow.

**API surface:**

|Method|Description|
|---|---|
|`read(key)`|Deserializes and returns the value for the given key. Returns `null` if absent.|
|`write(key, value)`|Serializes and stores the value. Throws a `StorageQuotaError` if the write fails due to capacity.|
|`remove(key)`|Deletes the key.|
|`getUsageEstimate()`|Returns an approximate byte count of all `ep_*` keys.|
|`exportAllAsPDF()`|Delegates to the Report Module to generate a PDF containing all stored expense data across all time periods. Returns a boolean indicating success.|
|`purgeByMonthRange(startMonth, endMonth)`|Deletes all expenses with dates falling within the specified month range (inclusive). Returns the count of deleted records.|

**Quota management flow:**

text

```
Write attempt fails with QuotaExceededError
        │
        ▼
Storage Service catches the error
        │
        ▼
Display storage-full dialog to user:
  "Your local storage is full. To continue adding
   expenses, please export your data and free up space."
        │
        ▼
User clicks "Export All Data as PDF"
        │
        ▼
Report Module generates a comprehensive PDF
containing all historical expenses grouped by month.
PDF is downloaded to the user's device.
        │
        ▼
User clicks "Free Up Space"
        │
        ▼
Display month-range selector:
  "Select months to delete (your data is saved in the PDF)."
  [Dropdown: From Month/Year] → [Dropdown: To Month/Year]
        │
        ▼
User confirms deletion range.
Storage Service calls purgeByMonthRange().
        │
        ▼
Storage is freed. Original write is retried.
```

**Key design decisions:**

- The purge operates on **month granularity**. Week-level deletion adds UI complexity with minimal storage benefit. Year-level deletion is too coarse.
- The PDF export is a **prerequisite** before purge is enabled. The purge button remains disabled until a successful export is confirmed in the current session. This prevents accidental data loss.
- A double-confirmation dialog is shown before purge execution.

### 5.4 Expense Module

**Purpose:** Business logic for expense CRUD, search, and filtering.

**API surface:**

|Method|Description|
|---|---|
|`create(name, amount, categoryId)`|Validates inputs, assigns ID and date, persists via Storage Service. Returns the new Expense object.|
|`update(id, fields)`|Partial update of an existing expense. Validates modified fields.|
|`delete(id)`|Removes a single expense by ID.|
|`getAll(filters)`|Returns expenses matching the provided filter criteria (date range, category IDs, search query).|
|`getTotalByCategory(dateRange)`|Returns a map of `categoryId → total amount` for the given date range.|
|`getGrandTotal(dateRange)`|Returns the sum of all expense amounts within the given date range.|

**Validation rules:**

- `name`: non-empty string, trimmed, max 100 characters.
- `amount`: positive number, rounded to 2 decimal places, must not exceed 999,999,999.99.
- `categoryId`: must reference an existing category ID.

### 5.5 Category Module

**Purpose:** Management of default and custom categories, including the deletion delegation flow.

**API surface:**

|Method|Description|
|---|---|
|`getDefaults()`|Returns the immutable list of default categories.|
|`getAll()`|Returns all categories (default + custom).|
|`createCustom(name, color)`|Creates a new custom category after uniqueness validation.|
|`deleteCustom(id, delegationStrategy, targetCategoryId?)`|Deletes a custom category. `delegationStrategy` is either `DELETE_EXPENSES` or `REASSIGN_EXPENSES`. If `REASSIGN_EXPENSES`, `targetCategoryId` is required.|
|`getExpenseCountForCategory(id)`|Returns the number of expenses associated with the given category.|

**Deletion delegation flow:**

1. Caller requests deletion of category `X`.
2. Category Module checks `isDefault`. If `true`, rejects with an error.
3. Category Module calls `getExpenseCountForCategory(X)`.
4. If count is 0, proceeds with immediate deletion.
5. If count > 0, returns a `DelegationRequired` response to the caller (the presentation layer), which renders the delegation modal.
6. Upon receiving the user's delegation choice, the Category Module either calls `Expense Module.delete()` for each associated expense or calls `Expense Module.update()` to reassign the `categoryId`.
7. The category record is then removed.

### 5.6 Report Module

**Purpose:** Time-based aggregation, currency formatting, and PDF generation.

**API surface:**

|Method|Description|
|---|---|
|`getWeeklyReport(weekStartDate)`|Returns aggregated data for the specified week.|
|`getMonthlyReport(year, month)`|Returns aggregated data for the specified month.|
|`getYearlyReport(year)`|Returns aggregated data for the specified year, including a per-month sub-breakdown.|
|`generatePDF(reportData, options)`|Produces a PDF document using jsPDF and jsPDF-AutoTable. Triggers a browser download. Returns a success/failure boolean.|
|`generateFullExportPDF()`|Generates a comprehensive PDF containing all stored data across all time periods. Used by the Storage Service during the quota management flow.|

**PDF structure:**

|Section|Content|
|---|---|
|Header|Application name, user name, generation timestamp.|
|Summary|Time period label, active currency, grand total.|
|Category Breakdown|Table: category name, total amount, percentage of grand total.|
|Itemized List|Table: date, name, category, amount. Sorted by date descending.|
|Footer|Page number, disclaimer ("Generated client-side. Verify amounts independently.").|

**jsPDF loading strategy:** The jsPDF and jsPDF-AutoTable scripts are loaded via CDN `<script>` tags with `defer`. The Report Module checks for the existence of the `jspdf` global before attempting generation. If unavailable (network failure, offline), the export function returns a failure status and the presentation layer displays an appropriate message.

### 5.7 Pet Module

**Purpose:** Canvas-based rendering and state management for the virtual cat companion.

**Subsystems:**

|Subsystem|Responsibility|
|---|---|
|**Renderer**|Manages the Canvas 2D context. Draws the current animation frame at the pet's position. Runs the `requestAnimationFrame` loop.|
|**Animation State Machine**|Determines the active animation based on pet state, elapsed time, and random selection. Transitions between states with defined durations.|
|**Hunger Engine**|Calculates hunger level on session start using `Time Service.elapsedHoursSince(lastVisitTimestamp)`. Updates hunger level on feed actions.|
|**Interaction Handler**|Processes feed and pet button clicks. Triggers corresponding animation transitions and state updates.|
|**Speech Bubble Manager**|Selects and displays contextual messages from a predefined pool. Timing is governed by an interval timer.|

**Animation state machine states:**

|State|Trigger|Duration|Transition|
|---|---|---|---|
|IDLE|Default|5–15s (random)|→ WALKING, LICKING, SLEEPING, PURRING, or ATTENTION (weighted random)|
|WALKING|Random from IDLE|3–6s|→ IDLE|
|LICKING|Random from IDLE|4–7s|→ IDLE|
|SLEEPING|Random from IDLE (low weight)|8–15s|→ IDLE|
|PURRING|Random from IDLE or after Pet interaction|2–4s|→ IDLE|
|HUNGRY|`elapsedHoursSince(lastVisit) >= 6`|Persistent until fed|→ EATING (on feed)|
|EATING|Feed button click|3s|→ IDLE (hunger reset)|
|PETTED|Pet button click|2s|→ IDLE|
|ATTENTION|Random from IDLE (medium weight)|4–6s|→ IDLE|

**Session lifecycle:**

|Event|Action|
|---|---|
|App load|Read `PetState` from storage. Calculate elapsed time since `lastVisitTimestamp`. Set initial animation state based on elapsed time and hunger level. Start render loop.|
|Every 5–15s|Animation State Machine evaluates transition.|
|Feed click|Set `lastFedTimestamp = now()`. Set `hungerLevel = 0`. Transition to EATING. Persist updated `PetState`.|
|Pet click|Increment `happinessLevel` (capped at 100). Transition to PETTED. Display positive speech bubble.|
|App unload / visibility change|Set `lastVisitTimestamp = now()`. Persist `PetState`. Stop render loop.|

## 6. Currency Formatting

Currency formatting is handled exclusively by the `Intl.NumberFormat` API, which is built into all modern browsers and requires no external data.

**Implementation approach:**

|Input|API Call|Output Example|
|---|---|---|
|`1234.5, "USD"`|`new Intl.NumberFormat(locale, { style: 'currency', currency: 'USD' })`|`$1,234.50`|
|`1234.5, "INR"`|Same pattern with `currency: 'INR'`|`₹1,234.50`|
|`1234, "JPY"`|Same pattern with `currency: 'JPY'`|`¥1,234` (no decimals)|

**Locale resolution:** The user's locale is detected via `navigator.language`. This ensures that number grouping separators and decimal marks follow the user's regional conventions (e.g., `1.234,50` in German locales vs `1,234.50` in US locales) while the currency symbol is determined by the selected currency code.

**Storage implication:** Amounts are stored as raw numbers (e.g., `1234.5`). Formatting is applied at render time only. Changing the active currency updates all displayed values immediately without modifying stored data.

## 7. Key Flows

### 7.1 Application Initialization

text

```
1. Storage Service reads ep_profile.
2. IF profile is null:
     → Trigger onboarding flow (collect username, pet name, pet skin, currency).
     → Persist profile and default categories.
     → Initialize PetState with current timestamp.
3. IF profile exists:
     → Load categories, expenses, and PetState from storage.
     → Time Service calculates elapsed time since lastVisitTimestamp.
     → Pet Module sets initial state based on elapsed time.
     → Report Module renders the default view (monthly, current month).
4. Attach visibilitychange and beforeunload listeners for session tracking.
```

### 7.2 Category Deletion with Delegation

text

```
1. User requests deletion of custom category C.
2. Category Module checks: isDefault(C) → true? Reject.
3. Category Module queries: count = Expense Module.getAll({ categoryId: C.id }).length.
4. IF count == 0:
     → Delete C. Done.
5. IF count > 0:
     → Return DelegationRequired(count) to presentation layer.
     → Presentation layer renders modal with two options:
         (a) "Delete all N expenses"
         (b) "Move all N expenses to [category dropdown]"
     → User selects option and confirms.
     → IF (a): Expense Module.delete() for each expense.
     → IF (b): Expense Module.update() categoryId for each expense.
     → Category Module deletes C.
```

### 7.3 Storage Quota Recovery

text

```
1. Storage Service.write() throws QuotaExceededError.
2. Presentation layer displays storage-full dialog.
3. User clicks "Export All Data."
4. Report Module.generateFullExportPDF() executes.
5. On successful download, "Free Up Space" button becomes enabled.
6. User selects month range [startMonth, endMonth].
7. User confirms deletion (double-confirmation).
8. Storage Service.purgeByMonthRange(startMonth, endMonth).
9. Storage Service retries the original write.
```

## 8. Error Handling

|Scenario|Detection|Response|
|---|---|---|
|Invalid expense input (empty name, negative amount)|Validation in Expense Module before persistence|Reject operation. Return validation error to presentation layer.|
|Deletion of default category|`isDefault` check in Category Module|Reject with descriptive error.|
|Category deletion with orphaned expenses|Expense count check in Category Module|Require delegation strategy before proceeding.|
|`localStorage` quota exceeded|`try/catch` around `localStorage.setItem` catching `QuotaExceededError`|Trigger export-then-purge flow (Section 7.3).|
|Corrupted JSON in `localStorage`|`try/catch` around `JSON.parse` in Storage Service.read()|Log warning. Return `null`. Treat as missing data. Trigger onboarding if profile is affected.|
|jsPDF CDN unavailable|Check for `window.jspdf` global before generation|Disable export button. Display tooltip: "PDF export unavailable. Check your connection."|
|Canvas API unsupported|Check for `HTMLCanvasElement.prototype.getContext`|Render static fallback image. Disable pet interactions.|
|Device clock is incorrect|Undetectable from client-side JS|Accepted limitation. Time-dependent features (hunger, greetings, period boundaries) will reflect the device clock. Documented in user-facing settings as a known constraint.|
|Concurrent tab modification|Not handled|Accepted limitation for a single-user tool. Last write wins.|

## 9. Performance Considerations

|Metric|Target|Approach|
|---|---|---|
|Initial load time|< 1s on 3G|Total payload < 200 KB (excluding CDN scripts). No build step, no framework overhead.|
|Expense list rendering|Smooth scroll at 1,000 entries|DOM recycling or pagination if entries exceed 200 in the current view.|
|Canvas animation|≥ 30 FPS|Limit sprite complexity. Use `requestAnimationFrame`. Pause rendering when tab is hidden (via `visibilitychange`).|
|PDF generation|< 3s for 500 expenses|jsPDF AutoTable handles batching internally. Generate off the main thread if needed (future optimization).|
|localStorage operations|< 10ms per read/write|Batch writes where possible. Avoid reading the entire expense array for single-record operations (future optimization: indexed lookups).|

## 10. Security and Privacy

|Concern|Mitigation|
|---|---|
|Data at rest|All data remains in the browser's `localStorage`. No data is transmitted to any server.|
|XSS via expense names|All user-provided strings are rendered via `textContent` (not `innerHTML`). Canvas text rendering is inherently safe from HTML injection.|
|Third-party CDN risk|jsPDF is loaded from a reputable CDN (jsDelivr or cdnjs). A Subresource Integrity (SRI) hash is included on the `<script>` tag to detect tampering.|
|Data deletion|The purge function removes records from `localStorage` irreversibly. The PDF export serves as the user's backup.|

## 11. Trade-offs and Alternatives Considered

|Decision|Alternative Considered|Rationale for Choice|
|---|---|---|
|`localStorage`|IndexedDB|IndexedDB supports larger storage and async operations but adds significant complexity for a data volume that fits comfortably in localStorage.|
|Custom ID generation|`crypto.randomUUID()`|`crypto.randomUUID()` is unavailable in non-secure contexts (HTTP without localhost). The custom composite ID works in all environments.|
|`Intl.NumberFormat` for currency|Manual symbol lookup table|`Intl` handles locale-specific formatting (decimal marks, grouping separators, symbol placement) automatically. A manual table would require maintaining hundreds of locale-currency combinations.|
|jsPDF via CDN|Server-side PDF generation|No server exists in this architecture. Client-side generation preserves the zero-infrastructure constraint.|
|Device clock for time|External NTP API (e.g., worldtimeapi.org)|An external API would break the offline-first, zero-dependency constraint. The device clock is accurate for the vast majority of users.|
|Month-granularity purge|Week-granularity or year-granularity|Week is too fine-grained for meaningful storage recovery. Year is too coarse and risks deleting data the user wants to keep. Month is the natural unit for expense review.|
|No framework|React, Vue, Svelte|A framework would require a build step, increase payload size by 30–150 KB, and add complexity disproportionate to the application's scope.|
